- (version) Inputs: platform specification v1.2 and content pipeline standard v2.2; requirements R01-R18 and invariants I01-I14 are normative.
- (constraint) Only T00/G0 design work is authorized; no product implementation, migrations, dependency upgrades, production rollout, or real client data.
- (decision) ADR-08 [ADOPTED]: GitLab Markdown repository is canonical; commit SHA is revision; MR is proposal; merge is apply; databases are rebuildable derivatives. Binds all stateful components and prevents dual canonical stores.
- (decision) ADR-09 [ADOPTED]: owner review UX lives in the platform over GitLab API; business owners need no GitLab accounts; GitLab MR UI remains engineering-only. Binds review and merge integration and prevents a second business review surface.
- (decision) ADR-10 [ADOPTED]: LDAP/OIDC identity adapter uses stable_id objectGUID/entryUUID/sub, versioned Git group mapping, JIT provisioning and revocation SLO <=30 minutes. Binds auth and ACL components and prevents email/login identity drift.
- (direction) Coaching path selected; primary audience is the engineering team; deliverables must support G0 review plus component design, ADR, database, integration specifications and epic/sprint planning; no PRD.
- (question) Resolve before G0: pre-publication bulk import versus I02; source-managed auto-merge versus R07; Space ACL versus page access metadata; merge identity for owners without GitLab accounts; stale ADR/test/standard references.
- (decision) Publication boundary selected in coaching: two phases. Before cutover, controlled engineering bulk push is allowed only to an unpublished main with no user access and no published index; expert sign-off and validation tag gate cutover. After cutover, protected main accepts managed changes only through GO and MR with human merge; agent/connector/LLM auto-merge is prohibited. Binds import, connectors, GO, UI state and CI; prevents silent bypass of review and resolves bulk-import/auto-merge drift.
- (decision) Two-level RBAC selected exactly from the platform specification: business users use Open WebUI upstream additive grants with scoped Reader/Author/Owner/Space admin/Instance admin capabilities and Space-level ACL inheritance in MVP; engineering users and bots use GitLab RBAC, protected main, CODEOWNERS and scoped tokens. Different ACLs require different Spaces. Page-level access front matter from the informational content standard is not an independent authorization source. Binds UI, tools, retrieval, files, history, export and merge; prevents divergent business and engineering authorization models.
- (constraint) Business owners must have no GitLab user records at all. Therefore GitLab cannot authenticate or natively approve their decisions; native CODEOWNERS approval cannot be the business approval mechanism. The design must attribute business decisions in platform/GO audit and Git MR metadata using trusted stable_id while a separate service identity performs the GitLab merge.
- (decision) Business merge gate selected: GO is the sole business merge orchestrator and only its merge service identity has GitLab merge permission for the business path. A versioned Git approval-policy.yaml maps external AD/OIDC groups to path-scoped approver roles; GO revalidates the approver's current external group, exact head SHA, base freshness, path scope and self-approval prohibition immediately before merge. CODEOWNERS remains engineering ownership/review context, not the business authorization source. The merge credential is never available to the agent, browser, CI indexer or connector. Binds GO, approval policy, UI, GitLab and audit; prevents absent GitLab user records from weakening review or attribution.
- (decision) Deployment boundary selected: minimal Open WebUI fork, separate GO deployable, and CI/index workers; one dedicated PostgreSQL instance per client with independently owned upstream, GO operational and retrieval/index schemas. Only GO holds the merge credential; component schemas must not be written cross-component. pgvector/FTS remains a T00-validated implementation candidate, not a pinned technology. Binds component APIs, data ownership and deployment planning; prevents merge-capability leakage and shared-table coupling.
- (decision) Canonical merge consistency specified by the user: before merge GO writes an MR DecisionRecord containing decision_id UUID used as the idempotency key, exact proposal_sha, base_sha, action, actor stable_id, timestamp and evidence. The business decision is canonical in Git, not PostgreSQL. The merge commit contains Decision-ID and Approved-by, so decision and result are linked in Git without GO. The GO decisions projection has unique(decision_id) and states recorded -> merge_attempted -> merged/failed/conflicted/invalid. One decision_id permits at most one merge; terminal truth is always derived from GitLab; the projection is fully rebuildable by reconciliation. Recovery: before DecisionRecord = safe retry; after record before merge = retry same decision_id; after merge before GO write = reconciliation finds the merge commit and marks merged without another merge. A returned non-error is not proof: only a merge commit in main confirms merged; timeout triggers reconciliation, never blind retry with a new decision_id. Binds GO, DB, GitLab integration, recovery and audit; prevents duplicate merges and loss of canonical audit.

- (direction) Defer physical Space-to-repository/root-folder mapping, first source connector, exact pgvector/index parameters, embedding model/dimensions, hoster model IDs, retention and non-revocation SLOs until the corresponding audit, benchmark or owner decision; logical contracts must not depend on a specific choice.
- (assumption) [ASSUMPTION] One PostgreSQL instance can host separate upstream, authorization, GO operations and index schemas with distinct roles; existing Open WebUI migrations remain upstream-owned. Confirm against the pinned upstream deployment during T00.
- (decision) DecisionRecord storage selected: canonical immutable structured GitLab MR note authored by GO, never a file/commit in the proposal branch and never mutable after creation. Document export is git clone plus a mandatory decisions manifest containing DecisionRecords and required MR metadata; external assets require their own manifest and backup. Binds GitLab adapter, merge protocol, reconciliation, backup and portability; prevents proposal_sha invalidation and loss of audit on export.
- (decision) Reconciliation clarification: initial publication requires a cutover record/tag bound to exact main SHA, expert sign-off, protected MR-only main, preflight index and subsequent Space activation; later business proposals require a real merge commit with Decision-ID and Approved-by trailers, so fast-forward-only publication is not eligible. Decision projection rebuild guarantees Git-derived current state, while transient attempt timestamps/errors may be disposable and retried under the same decision_id.
- (decision) Target-race resolution selected: every business and engineering merge goes through GO; no human or other service has direct merge permission after cutover. Engineering review/approval remains in GitLab UI, while final apply is invoked through GO. GO serializes merge critical sections per repository/target branch, re-reads target HEAD and requires HEAD == base_sha immediately before the GitLab merge with exact source proposal_sha. A target advance produces conflict/invalid and zero main writes; crash/timeout enters GitLab reconciliation under the same decision_id. Binds credentials, GitLab UI flow, HA locking and recovery; prevents target-branch TOCTOU.
- (decision) Decision durability selected: the same canonical DecisionRecord JSON and record_sha256 are written to an append-only GO MR note and a protected annotated Git tag kb-decisions/<decision_id> pointing at proposal_sha. The tag stores the full record without changing proposal_sha, is included in clone and anchors accepted, rejected and cancelled decisions. MR note is the API/UI representation; tag is the Git-native durability anchor; mismatched/missing note or tag makes the decision invalid. Decisions manifest remains mandatory for convenient export and verification.
- (decision) MVP physical perimeter selected: one GitLab repository equals exactly one Space. ACL, protected target branch, credentials, cutover, index snapshot, clone/export and backup share that perimeter; multiple ACL Spaces never share Git blobs or history. Binds repository provisioning, authz, indexing, export and epic decomposition; prevents cross-Space history disclosure and incompatible folder-level export semantics.
- (decision) Merge crash hardening: GO persists a per-repository/target recovery_required barrier before the external merge call. Any merge_attempted/unknown result blocks every new merge on that target, even after advisory lock loss or owner fencing. A new owner must complete target-wide reconciliation and prove the in-flight outcome resolved; timeout alone never clears the barrier and unprovable states remain quarantined. Squash, automatic rebase and fast-forward are disabled; accepted merge commits must have base_sha as first parent and proposal_sha as second parent plus matching Decision trailers.
- (decision) Companion hardening after technical review: authz-context-v2 carries independent policy/group/revocation bindings per Space; document-front-matter-v2 adds stable ID links, valid_until, provenance and strict archive/origin invariants without access; export-manifest-v2 closes decisions/assets/authorization; active index publication uses per-(Space,profile) CAS across all generations. Composite DB constraints bind every association to Space/repository/target/revisions. Binds UI/GO/CI/DB/contracts and prevents cross-Space confused-deputy and premature index/export states.
- (decision) Projection semantics: failed is guarded-retryable only after request completion and proven no-merge; conflicted/invalid are terminal; unknown remains merge_attempted + target recovery_required/quarantine and cannot clear without conclusive target-wide outcomes. Cutover preflight and published runs have different IDs but identical SHA/dependency closure; preflight never serves users. Canonical/projection mappings and CF-01..CF-30 T01 design vectors are companion contracts, not executed tests.

- (decision) ADR-17 [ADOPTED by project owner 2026-11-09]: GitLab is a platform data service outside every client application namespace and its release lifecycle. Tenant profile selects shared or dedicated GitLab: shared uses a private group per client and repository=Space with per-client credentials and backup/restore; dedicated uses the same pinned version and versioned configuration template but separate instance, secrets, endpoints, storage, network and backups without product code changes. Shared GitLab remains a common trust/failure domain requiring restricted admins, audit, reconciliation and per-client export/restore; common configuration never means common secrets. Binds deployment packaging, GO credentials, GitLab provisioning and portability; prevents namespace-coupled data deletion, cross-client identities/backups and divergent client deployment models.
